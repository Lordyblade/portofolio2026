Laporan Akhir: Project UangKu - Expensed Tracker

Ibrahim Mousa Dhani 2411532010

A. Pendahuluan

Pengelolaan keuangan pribadi memerlukan pencatatan pemasukan dan pengeluaran yang teratur agar pengguna dapat mengetahui perubahan saldo serta meninjau transaksi yang telah dilakukan. Aplikasi pada perangkat bergerak dapat membantu proses tersebut karena informasi dapat dicatat dan diperiksa secara langsung melalui satu antarmuka.

Berdasarkan kebutuhan tersebut, dikembangkan UangKu - Expense Tracker, yaitu aplikasi pencatatan keuangan berbasis Flutter yang merupakan kelanjutan dari materi Praktikum I sampai Praktikum V. Materi widget dan manajemen state, penyusunan layout, input dan validasi formulir, serta navigasi digabungkan dengan fitur Login, Register, dan penyimpanan lokal menggunakan SQLite.

Pada versi ini, pengguna dapat membuat akun, masuk menggunakan akun tersebut, menambahkan transaksi pemasukan atau pengeluaran, melihat saldo dan riwayat transaksi, serta membuka informasi profil. Data akun dan transaksi disimpan pada database lokal perangkat. Oleh karena itu, data dapat dibaca kembali setelah aplikasi dibuka ulang selama data aplikasi tidak dihapus atau aplikasi tidak diuninstal. Laporan ini menjelaskan teori pendukung, struktur berkas, implementasi fitur, serta keluaran yang diharapkan dari aplikasi.

B. Tujuan

Pengembangan UangKu - Expense Tracker bertujuan menghasilkan aplikasi pencatatan keuangan berbasis Flutter yang menggabungkan fitur navigasi, autentikasi pengguna, dan penyimpanan data lokal. Secara khusus, tujuan pengembangan ini adalah sebagai berikut:

  • Mengintegrasikan halaman Dashboard, Catat Transaksi, Detail Transaksi, Riwayat, Login, Register, dan Profil dalam satu aplikasi.
  • Menyediakan proses Register dan Login dengan validasi input serta pemeriksaan akun yang tersimpan secara lokal.
  • Menggunakan SQLite untuk menyimpan akun dan transaksi sehingga data dapat dibaca kembali setelah aplikasi ditutup dan dibuka ulang.
  • Menghitung saldo berdasarkan pemasukan dan pengeluaran serta menampilkan riwayat transaksi sesuai akun yang sedang login.

C. Alat

Perangkat dan dependensi yang digunakan selama praktikum:

  • Flutter SDK
  • Code Editor : VS Code atau Android Studio.
  • Emulator Android atau perangkat fisik untuk menjalankan aplikasi.
  • Proyek Flutter dari Praktikum IV yang berisi halaman Dashboard, form tambah transaksi, dan detail transaksi.
  • Paket Flutter: sqflite, path, crypto, dan intl.
  • Perangkat Android atau emulator dengan dukungan SQLite.

D. Dasar Teori

Named Routes
Named Routes adalah metode navigasi Flutter yang menggunakan nama berupa string untuk mengakses halaman. Nama rute didaftarkan pada properti routes di MaterialApp, sehingga pemanggilan halaman tidak perlu menuliskan MaterialPageRoute berulang kali di setiap tombol. Pada praktikum ini, rute “/” digunakan untuk halaman utama yang memiliki tab, sedangkan rute “/add” digunakan untuk halaman tambah transaksi.

Properti initialRoute menentukan halaman pertama yang dibuka. Sementara itu, routes berisi pemetaan nama rute dengan widget yang akan ditampilkan. Setelah rute didaftarkan, perpindahan dapat dilakukan dengan Navigator.pushNamed(context, “/add”).

Bottom Navigation Bar
BottomNavigationBar merupakan menu navigasi yang diletakkan di bagian bawah layar. Menu ini dapat digunakan untuk berpindah antara halaman utama seperti Beranda, Riwayat, dan Profil tanpa harus membangun navigasi baru pada setiap halaman.

Properti currentIndex menunjukkan tab yang sedang aktif, sedangkan items berisi ikon dan label tiap tab. Ketika pengguna memilih tab, fungsi onTap menerima indeks pilihan. Nilai indeks kemudian diubah menggunakan setState() agar Flutter membangun ulang tampilan dengan halaman yang sesuai.

Penyimpanan Lokal Menggunakan SQLite
SQLite adalah basis data relasional yang disimpan sebagai berkas pada perangkat. Pada aplikasi ini, SQLite digunakan untuk menyimpan data pengguna dan transaksi melalui paket sqflite. Data tidak hanya berada di variabel atau daftar sementara pada memori, tetapi ditulis ke tabel database sehingga dapat dibaca kembali ketika aplikasi dibuka ulang. Penyimpanan ini bersifat lokal pada perangkat dan tidak otomatis tersinkron ke perangkat lain.

Tabel users menyimpan identitas pengguna, email unik, serta hash dan salt password. Tabel transactions menyimpan transaksi yang berkaitan dengan pengguna melalui user_id. Relasi tersebut membuat setiap pengguna hanya melihat transaksi miliknya. Primary key digunakan sebagai identitas baris, sedangkan batasan UNIQUE pada email membantu mencegah pendaftaran akun dengan email yang sama.

Login dan Register
Register merupakan proses pembuatan akun baru dengan mengisi nama, email, password, dan konfirmasi password. Form memvalidasi data sebelum akun disimpan. Login memeriksa email dan password terhadap data yang sudah tersimpan di SQLite. Jika cocok, aplikasi meneruskan data pengguna ke halaman utama; jika tidak cocok, aplikasi menampilkan pesan kegagalan dan tetap berada pada halaman Login.

Untuk demonstrasi lokal ini, password tidak disimpan sebagai teks biasa. Aplikasi menyimpan hash SHA-256 bersama salt acak. Pendekatan ini membantu menghindari penyimpanan password mentah, tetapi tetap merupakan implementasi pembelajaran lokal dan bukan pengganti sistem autentikasi produksi yang dirancang khusus untuk keamanan.

E. Langkah-Langkah Pengembangan Aplikasi

Proyek UangKu - Expense Tracker ini melanjutkan dari praktikum-praktikum sebelumnya. Pada tahap awal, pastikan file main.dart, dashboard_screen.dart, add_transaction_screen.dart, dan transaction_detail_screen.dart tersedia di dalam folder lib (dari Praktikum IV). Selanjutnya, main_screen.dart digunakan sebagai penampung tab utama, sementara history_screen.dart dan profile_screen.dart dikembangkan lebih lanjut (dari Praktikum V). Untuk versi lanjutan dalam laporan ini, ditambahkan login_screen.dart, register_screen.dart, dan app_database.dart untuk mengelola autentikasi serta penyimpanan akun dan transaksi di SQLite.

1. Mendaftarkan Named Routes pada main.dart

Pada file main.dart, pemanggilan halaman awal melalui properti home diganti dengan initialRoute dan routes. Dengan cara ini, halaman utama diakses melalui rute “/”, sedangkan halaman tambah transaksi diakses melalui rute “/add”.

Bagian initialRoute: “/” menetapkan MainScreen sebagai halaman pertama. Pemetaan di dalam routes menghubungkan setiap nama rute dengan widget tujuan. Baris yang mengarah ke AddTransactionScreen memungkinkan layar input transaksi dibuka melalui nama rute, bukan dengan membuat MaterialPageRoute secara langsung.

2. Membuat MainScreen sebagai Penampung Tab

Buat file main_screen.dart. Widget MainScreen menggunakan StatefulWidget karena indeks tab aktif dapat berubah ketika pengguna memilih menu yang berbeda. Variabel _selectedIndex dimulai dari 0 sehingga tab Beranda aktif ketika halaman pertama kali dibuka.

List _pages menampung widget yang ditampilkan. Dalam versi dasar modul, halaman Dashboard diambil dari Praktikum IV, halaman Riwayat masih berupa teks sementara, dan halaman Profil mengarah ke ProfileScreen. Setelah pengguna memilih menu, fungsi _onItemTapped() memanggil setState() untuk memperbarui _selectedIndex. Bagian body kemudian menampilkan widget sesuai indeks yang aktif.

BottomNavigationBar memiliki tiga item, yaitu Beranda, Riwayat, dan Profil. Nilai currentIndex mengikuti _selectedIndex, sementara onTap menjalankan _onItemTapped. Dengan susunan ini, navigasi antartab dikelola dari satu Scaffold utama.

3. Memperbarui Tombol Tambah pada Dashboard

Buka dashboard_screen.dart yang sudah dibuat pada Praktikum IV. Pada bagian floatingActionButton, ganti navigasi berbasis Navigator.push dan MaterialPageRoute dengan Navigator.pushNamed. Rute “/add” sudah terdaftar pada main.dart sehingga tombol dapat memanggilnya secara langsung.

Ketika tombol tambah ditekan, Flutter membuka AddTransactionScreen melalui rute “/add”. Setelah pengguna menutup halaman tersebut dengan Navigator.pop(), aplikasi kembali ke halaman sebelumnya, yaitu Dashboard.

4. Membuat Halaman Riwayat Transaksi

Buat file history_screen.dart. Halaman ini menampilkan beberapa contoh transaksi dalam bentuk daftar. Data masih ditulis langsung pada kode untuk keperluan tampilan, sehingga belum mengambil data secara dinamis dari penyimpanan aplikasi.

List transactions menyimpan contoh judul, nominal, kategori, tanggal, dan jenis transaksi. ListView.builder menampilkan data tersebut satu per satu. Warna hijau digunakan untuk pemasukan, sedangkan warna merah digunakan untuk pengeluaran agar keduanya mudah dibedakan.

5. Membuat Halaman Profil

Buat atau perbarui file profile_screen.dart. Halaman ini menampilkan avatar, nama pengguna, email, dan tombol Logout. Email diterima melalui constructor dari halaman utama. Agar nama tidak hanya berupa teks tetap, halaman Profil menggunakan getter _displayName untuk membentuk nama tampilan dari bagian alamat email sebelum tanda @. Dengan demikian, isi Profil mengikuti email yang dimasukkan pada halaman Login, tanpa memerlukan kolom nama tambahan.

Getter _displayName mengambil bagian email sebelum tanda @, menghapus angka, mengganti pemisah seperti titik, garis bawah, dan tanda hubung menjadi spasi, lalu mengubah huruf awal setiap kata menjadi kapital. Contohnya, email ibrahim.mousa@gmail.com ditampilkan sebagai “Ibrahim Mousa”. Nama tersebut merupakan nama tampilan yang diperkirakan dari email, bukan nama asli yang diambil dari akun atau database; jika nama asli harus diinput pengguna, formulir Login perlu ditambah kolom Nama. Tombol Logout menggunakan Navigator.pushNamedAndRemoveUntil untuk kembali ke halaman Login sekaligus menghapus rute sebelumnya dari tumpukan navigasi, sehingga pengguna tidak langsung kembali ke halaman utama menggunakan tombol kembali setelah logout.

6. Membuat Halaman Login

Buat file login_screen.dart. Form Login memiliki TextFormField untuk email dan password. Validasi memastikan email tidak kosong dan memiliki karakter “@”, serta password wajib diisi. Karena tugas berfokus pada navigasi dan pengiriman data, login ini hanya berupa simulasi antarmuka dan belum melakukan pemeriksaan akun melalui server atau database.

Ketika tombol Login ditekan, fungsi _login() memeriksa validitas form. Jika valid, email yang telah di-trim dikirim melalui argumen pada Navigator.pushReplacementNamed(context, "/", arguments: email). Rute halaman Login digantikan oleh halaman utama sehingga pengguna berpindah ke aplikasi tanpa menumpuk halaman Login di atasnya.

7. Mengintegrasikan Rute Login

Agar aplikasi latihan dimulai dari Login, ubah main.dart. Versi dasar pada langkah praktikum menggunakan initialRoute “/”, sedangkan versi latihan menggunakan initialRoute “login” tanpa garis miring awal. Penamaan ini menghindari perilaku Flutter yang dapat membentuk rute “/” sebagai rute perantara saat menyusun initial route. Rute “/” tetap mengarah ke MainScreen dan rute “/add” tetap mengarah ke AddTransactionScreen.

Perubahan initialRoute tersebut diperlukan hanya untuk memenuhi alur Login pada tugas. Pada tahap dasar Named Routes, initialRoute “/” tetap sesuai dengan urutan yang diberikan dalam modul. Nama rute “login” tanpa garis miring awal digunakan khusus pada versi latihan agar layar Login dibuka sebagai satu rute awal.

8. Memperbarui MainScreen untuk Menampilkan Email dan Halaman Riwayat

Perbarui file main_screen.dart agar daftar halaman menggunakan HistoryScreen yang sudah dibuat. MainScreen membaca email dari argumen rute melalui ModalRoute.of(context)?.settings.arguments. Email tersebut diteruskan ke DashboardScreen dan ProfileScreen. Pada Dashboard, nama tampilan dibuat dari bagian email sebelum tanda @, sedangkan alamat email lengkap tetap ditampilkan di bawah sapaan.

Pada versi akhir ini, Dashboard menerima email dari halaman Login melalui argumen named route. Getter _displayName membentuk nama tampilan dari bagian email sebelum tanda @ dengan mengganti pemisah titik, garis bawah, atau tanda hubung menjadi spasi, menghapus angka, dan mengubah huruf awal setiap kata menjadi kapital. Contohnya, ibrahim.mousa@gmail.com akan menghasilkan sapaan “Halo, Ibrahim Mousa”. Alamat email lengkap juga ditampilkan pada baris tersendiri di bawah sapaan. Tampilan saldo, daftar transaksi, dan tombol tambah tetap dipertahankan dari Dashboard Praktikum IV; tombol tambah menggunakan named route “/add” sesuai Modul V.

Variabel displayedEmail memastikan alamat email dari Login ditampilkan apa adanya setelah spasi di awal atau akhir dihilangkan. Sementara itu, $_displayName merujuk pada getter yang mengubah bagian nama sebelum tanda @ menjadi nama tampilan yang lebih mudah dibaca. Nama tersebut hanya perkiraan berdasarkan teks email dan bukan nama asli yang diverifikasi.

Implementasi Fitur Lanjutan UangKu

Halaman Dashboard, navigasi bawah, dan alur pencatatan transaksi tetap dipertahankan dengan gaya visual utama berwarna merah. Halaman Login dan Register ditambahkan sebagai tampilan baru, sedangkan data akun dan transaksi disimpan melalui SQLite. Dengan perubahan ini, daftar transaksi dan saldo tidak lagi hanya mengandalkan data statis yang ditulis langsung pada widget.

9. Menghubungkan Halaman Riwayat dengan SQLite

Pada implementasi awal, daftar Riwayat menggunakan data contoh yang ditulis di dalam kode. Pada versi lanjutan, HistoryScreen menerima userId dan mengambil transaksi milik pengguna dari AppDatabase. Data dimuat kembali ketika tab Riwayat dibuka sehingga transaksi yang baru disimpan dapat ditampilkan. Setiap item menampilkan judul, kategori, tanggal, nominal, dan warna yang membedakan pemasukan dengan pengeluaran.

Kode tersebut menunjukkan bahwa halaman Riwayat tidak lagi membuat daftar contoh secara lokal pada setiap render. Fungsi getTransactions mengambil data dari tabel transactions berdasarkan user_id, kemudian hasil query disimpan pada state untuk ditampilkan oleh ListView.builder. Karena menggunakan data dari database, riwayat dapat dibaca kembali setelah aplikasi dibuka ulang.

10. Membuat Halaman Profil dan Logout

Halaman Profil menampilkan nama dan email yang tersimpan untuk akun yang sedang login. Data pengguna diteruskan sebagai Map dari hasil Login atau Register. Tombol Logout menghapus halaman utama dari tumpukan navigasi dan mengembalikan pengguna ke halaman Login. Logout tidak menghapus data akun atau transaksi di SQLite, sehingga pengguna dapat masuk kembali menggunakan akun yang sama.

Ketika tombol Logout ditekan, aplikasi menghapus halaman-halaman sebelumnya dari tumpukan navigasi dan kembali ke Login. Data yang tersimpan di SQLite tetap dipertahankan.

11. Mengembangkan Halaman Login

Halaman Login menyediakan kolom email dan password serta tautan menuju Register. Sebelum pemeriksaan akun dijalankan, form memvalidasi bahwa email diisi dengan format yang sesuai dan password tidak kosong. Selanjutnya, fungsi loginUser pada AppDatabase mencari akun berdasarkan email dan mencocokkan hash password. Jika data tidak sesuai, aplikasi menampilkan pesan kesalahan. Jika cocok, data pengguna diteruskan ke rute /home.

12. Menambahkan Halaman Register

Halaman Register merupakan fitur baru yang melengkapi Login simulasi pada versi latihan awal. Pengguna mengisi nama lengkap, email, password, dan konfirmasi password. Form memeriksa kolom wajib, format email, panjang password minimal enam karakter, serta kecocokan konfirmasi password. Setelah validasi berhasil, aplikasi memanggil registerUser untuk menyimpan akun baru di tabel users. Email dibuat unik agar tidak dapat digunakan oleh dua akun yang berbeda. Setelah berhasil mendaftar, pengguna langsung diarahkan ke halaman utama.

Contoh validator email memeriksa kolom kosong dan format alamat email sebelum data dikirim ke database:

Jika email sudah pernah digunakan, SQLite menolak data karena kolom email memiliki batasan UNIQUE. Aplikasi kemudian menampilkan pesan bahwa email telah terdaftar. Dengan demikian, proses Register dan Login menggunakan data akun yang sama, bukan data contoh yang hanya berlaku selama aplikasi berjalan.

13. Membuat Database Lokal dengan SQLite

File app_database.dart bertanggung jawab menyiapkan basis data dan menyediakan operasi untuk membuat akun, memeriksa akun saat Login, membaca transaksi, menghitung saldo, serta menyimpan transaksi baru. Database dibuat dengan nama expense_tracker.db. Tabel users menyimpan informasi akun, sementara tabel transactions menyimpan transaksi dan menghubungkannya dengan pemilik melalui user_id.

Operasi penyimpanan dijalankan melalui metode asynchronous agar antarmuka tetap responsif ketika database diakses. Password tidak disimpan sebagai teks biasa; aplikasi membuat salt acak dan menyimpan hasil hash bersama salt tersebut. Ketika Login dilakukan, hash dihitung kembali dari salt dan password yang dimasukkan, lalu dibandingkan dengan nilai yang tersimpan. Implementasi hashing ini ditujukan untuk kebutuhan pembelajaran lokal dan belum dimaksudkan sebagai mekanisme autentikasi produksi.

Ketika akun baru dibuat, aplikasi juga menambahkan dua transaksi contoh, yaitu Makan Siang dan Gaji Bulanan, untuk menjaga agar tampilan awal tetap mendekati contoh Dashboard pada modul. Kedua data tersebut masuk ke SQLite satu kali saat Register berhasil dan tidak dibuat ulang ketika halaman dibangun. Transaksi baru yang dimasukkan pengguna juga disimpan pada tabel yang sama.

14. Mengintegrasikan Named Routes dan Data Pengguna

Pada versi terintegrasi, aplikasi dimulai dari Login. Named routes digunakan untuk mengatur perpindahan ke Login, Register, halaman utama, dan form tambah transaksi. Rute /home menerima objek user dari hasil Login atau Register. Rute /add menerima userId agar transaksi yang disimpan tercatat sebagai milik pengguna yang sedang masuk.

MainScreen bertindak sebagai wadah untuk tiga tab utama. Dashboard menerima data user untuk menampilkan nama dan email, HistoryScreen menerima userId untuk membaca transaksi milik akun yang sedang aktif, dan ProfileScreen menerima data pengguna yang sama. Body menampilkan halaman berdasarkan indeks tab yang dipilih sehingga BottomNavigationBar tetap menjadi navigasi utama.

15. Menyimpan Transaksi dari Form

Form Catat Transaksi mempertahankan masukan judul, nominal, jenis transaksi, kategori, dan tanggal. Data divalidasi sebelum disimpan. Nominal harus berupa angka positif, tanggal harus dipilih, dan kolom yang diwajibkan tidak boleh kosong. Ketika tombol Simpan ditekan, addTransaction menulis data ke SQLite berdasarkan userId akun aktif. Setelah penyimpanan berhasil, halaman form ditutup dan Dashboard memuat ulang saldo serta transaksi terakhir.

Dashboard menghitung saldo dari seluruh transaksi tersimpan: pemasukan menambah saldo dan pengeluaran mengurangi saldo. Dengan demikian, nominal saldo tidak hanya berupa angka statis, melainkan berubah mengikuti transaksi yang dicatat pengguna. Riwayat mengambil catatan yang sama dari database, sehingga data pada Dashboard dan Riwayat bersumber dari penyimpanan yang konsisten.

G. Output Aplikasi

Pengujian Halaman Register
Pengujian dilakukan dengan memasukkan nama pengguna, alamat email, kata sandi, dan konfirmasi kata sandi pada halaman Register. Setelah tombol Register ditekan, diperiksa apakah akun berhasil dibuat dan disimpan ke dalam database SQLite. Pengujian juga dilakukan dengan memasukkan data yang tidak lengkap, kata sandi yang tidak sesuai, atau email yang sudah terdaftar untuk memastikan aplikasi memberikan respons yang sesuai.

Pengujian Halaman Login
Pengujian dilakukan dengan memasukkan email dan kata sandi dari akun yang telah terdaftar. Setelah tombol Login ditekan, diperiksa apakah aplikasi berhasil mengarahkan pengguna ke halaman utama. Selain itu, pengujian dilakukan menggunakan email atau kata sandi yang salah untuk memastikan aplikasi menolak proses login dan menampilkan pesan yang sesuai.

Pengujian Halaman Dashboard
Pengujian dilakukan dengan memeriksa tampilan Dashboard setelah pengguna berhasil Login. Hal yang diperiksa meliputi sapaan nama pengguna, alamat email, informasi saldo, dan daftar transaksi terbaru. Pengujian ini bertujuan memastikan informasi yang ditampilkan sesuai dengan data pengguna dan transaksi yang tersimpan di dalam database.

Pengujian Halaman Catat Transaksi
Pengujian dilakukan dengan memasukkan data transaksi berupa judul, nominal, jenis transaksi, kategori, dan tanggal. Setelah tombol Simpan ditekan, diperiksa apakah data transaksi berhasil disimpan ke SQLite dan apakah aplikasi memberikan respons yang sesuai. Pengujian juga dilakukan dengan membiarkan kolom wajib kosong untuk memastikan validasi formulir berjalan dengan baik.

Pengujian Halaman Detail Transaksi
Pengujian dilakukan dengan memilih salah satu transaksi pada Dashboard atau halaman Riwayat. Selanjutnya, diperiksa apakah halaman Detail Transaksi menampilkan informasi yang sesuai dengan transaksi yang dipilih, seperti judul, nominal, kategori, jenis transaksi, dan tanggal. Pengujian ini bertujuan memastikan data transaksi diteruskan dan ditampilkan dengan benar.

Pengujian Halaman Riwayat
Pengujian dilakukan dengan membuka menu Riwayat melalui Bottom Navigation Bar. Diperiksa apakah daftar transaksi yang sebelumnya disimpan dapat ditampilkan dengan benar, termasuk informasi pemasukan dan pengeluaran. Pengujian juga dilakukan setelah menambahkan transaksi baru untuk memastikan data tersebut muncul pada halaman Riwayat.

Pengujian Halaman Profil
Pengujian dilakukan dengan membuka menu Profil melalui Bottom Navigation Bar. Hal yang diperiksa meliputi tampilan foto atau avatar, nama pengguna, alamat email, dan tombol Logout. Pengujian ini bertujuan memastikan informasi akun ditampilkan dengan benar serta tombol Logout dapat digunakan untuk mengakhiri sesi pengguna dan kembali ke halaman Login.

Pengujian Halaman Data Lokal
Pengujian dilakukan dengan mendaftarkan akun, Login, dan menambahkan beberapa transaksi ke dalam aplikasi. Setelah itu, aplikasi ditutup dan dibuka kembali, kemudian pengguna melakukan Login menggunakan akun yang sama. Diperiksa apakah akun masih dapat digunakan dan data transaksi sebelumnya tetap tersedia pada Dashboard maupun halaman Riwayat. Pengujian ini bertujuan memastikan SQLite menyimpan data secara lokal sehingga data tidak hilang hanya karena aplikasi ditutup atau pengguna melakukan Logout.

H. Kesimpulan

Berdasarkan pengembangan aplikasi UangKu – Expense Tracker, dapat disimpulkan bahwa aplikasi ini dirancang untuk membantu pengguna mencatat dan mengelola pemasukan serta pengeluaran keuangan secara lebih teratur. Aplikasi ini memiliki fitur Register dan Login untuk mengelola akun pengguna, Dashboard untuk menampilkan informasi saldo dan transaksi terbaru, halaman Catat Transaksi untuk memasukkan data transaksi, serta halaman Riwayat untuk melihat transaksi yang telah dicatat. Selain itu, halaman Profil digunakan untuk menampilkan informasi pengguna dan menyediakan fitur Logout.

Penyimpanan data menggunakan SQLite diterapkan agar informasi akun dan transaksi dapat disimpan secara lokal pada perangkat, sehingga data tidak hanya bergantung pada data statis di dalam kode program. Penerapan navigasi menggunakan Named Routes dan Bottom Navigation Bar juga membantu pengguna berpindah ant halaman sesuai kebutuhan. Dengan fitur-fitur tersebut, UangKu diharapkan dapat menjadi aplikasi pencatatan keuangan sederhana yang mudah digunakan dan membantu pengguna memantau kondisi keuangannya dengan lebih baik.

I. Saran dan Pengembangan Berikutnya

Penyimpanan SQLite bersifat lokal, sehingga data tidak tersedia secara otomatis di perangkat lain dan dapat hilang jika pengguna menghapus data aplikasi atau melakukan uninstall. Untuk aplikasi yang digunakan secara nyata, keamanan autentikasi perlu ditingkatkan, misalnya dengan pendekatan hashing password yang dirancang khusus untuk password dan pengujian keamanan yang lebih menyeluruh. Fitur ekspor/cadangan database, ubah/hapus transaksi, serta sinkronisasi online dapat dikembangkan pada tahap berikutnya apabila dibutuhkan.
